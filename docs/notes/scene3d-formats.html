3D file formats: UNLW scenes, LWV objects and UEXP scenes

The demo has no 3D model loader of the usual kind: every 3D file is a small pre-digested binary produced by the group's own converters. *.lwe (magic UNLW) is a LightWave scene reduced to its motion data (objects, nulls, one camera, lights), *.lwv is the LightWave object that an .lwe refers to (the loader at 0x1cacc simply patches the name x.lwo into x.lwv and opens it in the archive), and *.exp (UEXP) is an export of a 3D Studio MAX scene (Box01, GeoSphere01, Omni01... are MAX names). The loaders are handwritten assembly (loadlws.c at 0x1bf7c, loaduexp.c at 0x1f02f) that read the whole file into memory and then walk a pointer through it.

A UNLW file is a stream of tagged chunks; the dispatcher is a jump table indexed by the tag byte. Every animated entity is a list of 44-byte motion keys: six floats (x y z, heading pitch bank in degrees), the frame number, a linear flag and the tension / continuity / bias of the Kochanek-Bartels spline. The loader turns them into a doubly linked list of 0x58-byte records (values widened to doubles) and appends a copy of the last key as sentinel. The last six dwords of the file give the entity counts and the duration in frames (1500 for the aziz scene, 160 for obj1.lwe).

; 0x1c116  chunk dispatcher of loadlws.c  (ah = chunk id = byte before the read pointer ebp)
1c10a  mov  ah, byte ptr [ebp - 1]
1c10d  cmp  ah, 0xff                 ; 0xff = end
1c110  je   0x1ca74
1c116  mov  al, ah
1c118  dec  al
1c11a  cmp  al, 0xa
1c11c  ja   0x1ca6b                  ; unknown id: skip
1c126  jmp  dword ptr cs:[edx*4 + 0x1bf50]   ; 1 object, 2 camera, 3 light, 4 null, 11 modifier
; object key reader (0x1c1eb): 44 bytes -> 0x58 byte record, floats widened to doubles
1c1eb  add  ebp, 4
1c1f4  fld  dword ptr [ebp - 4]      ; x
1c1fa  fstp qword ptr [esi + eax]
...                                  ; y z heading pitch bank the same way
1c24d  mov  edi, dword ptr [ebp + 4] ; frame number
1c253  mov  dword ptr [esi + eax + 0x4c], edi
1c260  mov  edi, dword ptr [ebp + 4] ; linear flag
1c266  mov  dword ptr [esi + eax - 0x10], edi
1c271  fld  dword ptr [ebp + 4]       ; tension, continuity, bias
1c274  fstp qword ptr [esi + eax - 0x28]

// formats.js: parseLWE (chunk loop) and the key reader
function readLweKeys(dv, p, n) {
  for (let i = 0; i < n; i++, p += 44) {
    for (let k = 0; k < 6; k++) v[k] = dv.getFloat32(p + 4 * k, true);
    keys.push({ v, frame: dv.getInt32(p + 24, true), linear: dv.getInt32(p + 28, true) !== 0,
      tension: dv.getFloat32(p + 32, true), continuity: dv.getFloat32(p + 36, true), bias: dv.getFloat32(p + 40, true) });
  }
}

LWV objects

12-byte header (vertices, triangles, surfaces), then 20 bytes per vertex (x y z u v), one 70-byte record per surface (name[32], texture name[26], RGB at +58, flags) and 8 bytes per triangle (three 16-bit vertex indices and a surface number). Only one surface exists in the four shipped objects and all of them point at the same 256x256 texture (echo.png, echo2.png, test.png), used as an environment map. The values of the script commands lwotr (transparency, 0-255) and lwoshading (shading mode) that were in force when the scene was loaded are copied into every surface record (+0xa7 and +0xa6), which is why aziz1.lwe / obj1.lwe are opaque (255) and aziz2.lwe, loaded after lwotr 57, is 22 % transparent.

UEXP

Header: object / camera / null / light / particle / material counts and the duration in frames. A material is 16+5*13 name bytes, nine floats and four bytes (shininess, opacity, shading mode, flags: the boxes use mode 4, opacity 160 or 255). Objects store their vertices in world space (the loader multiplies them with the inverse node matrix), UV set, faces (3 indices + material) and a position track; cameras are a position and a target track plus FOV / roll tracks (a 3ds-max target camera), lights a name, colour and a position track. Tracks are 28-byte keys (frame, x, y, z, tension, continuity, bias) evaluated by the same TCB spline.
