echo4 - additive 3D cage with glow trails (and the 3D triangle pipeline)

A tiny software 3D engine hides behind the "echo" names. echo4 builds a cage of 3 x 6 square planes (at +-100, +-60, +-20 along every axis, 72 vertices, 36 triangles), rotates it with three angles derived from the (differentiated) expression, pushes it 500 units away and draws every triangle additively into the 8 bit buffer with a perspective-correct texture mapper; the texture is 2500 random soft blobs generated at start (the original used rand(), the port reproduces the generator from the seed measured in the original). Because adding commutes, the triangles need no depth sort (the original still files them into 4096 depth buckets and drops anything farther than index 4095). The finished picture is then smeared: every pixel gets 0.65 x the (already smeared) pixel to its left and then above it, which stretches the bright additive line crossings into long glow trails.

The expression parameter (Frame*0.8) is not a value but a clock: only its change since the previous frame (dt) is used, it advances the angle (+0.00225 per unit) and scrolls the texture. Each frame builds a 3x4 float matrix by calling small routines (identity, three rotations, scale 3.5/4.55/3.5, translation 500) and multiplies every vertex (0x8ba34). Triangles go through a 4 stage clipper (the four side planes |x|<z, |y|<z, implemented by testing the sign of x-z, negating/swapping the coordinates between stages and clipping with linear interpolation into scratch vertices; the code is shared with the rest of the demo's polygon engine) and the rasteriser 0x8985d: vertices are projected to 16.16 fixed point (note the stored screen axes: x uses scale 160 px, y 100 px), u/z, v/z and 1/z are interpolated with gradients solved from the triangle's edge vectors, edges are stepped Bresenham style (the carry of the low 16 bits selects between two precomputed attribute steps), and inside a scanline 1/z is inverted only every 8 pixels - the texture coordinates of the 8 pixels are linear in between.

The pixel loop packs both texture coordinates in one 32-bit register (U as 8.8 in the high half, V in the low half): one add ebx,eax moves both, the two bytes that are the integer parts are extracted with shr edx,24 / mov dh,bh. It is unrolled eight times and entered in the middle (jump table at 0xd4570) for the remainder pixels of a span. All of this is replicated bit-exactly in the port (the clipper, the sub-pixel set-up and the packed arithmetic, including its carry quirk).

89fa4  mov eax, dword ptr [0xceed4]; step per pixel = (end-start)/8 for U (high half) and V (low half) packed in one register
89fa9  shl eax, 0x10; U step << 16
89fac  mov ax, word ptr [0xceedc]; | V step (16 bits)
89fb2  mov dword ptr [0xcef14], eax
89fb7  mov ebx, dword ptr [0xceec4]; ebx = U<<16 | V : two 8.8 fixed point texture coordinates in one dword
89fbd  shl ebx, 0x10; U in the high half
89fc0  mov bx, word ptr [0xceecc]; V in the low half
89fc7  mov esi, dword ptr [0xceeb4]; esi = texture (256x256 bytes)
89fcd  mov ecx, edx
89fcf  mov edx, ebx; texel offset = (V int << 8) | U int
89fd1  shr edx, 0x18; edx = U integer (bits 24-31)
89fd4  mov dh, bh; dh = V integer (bits 8-15 of ebx)
89fd6  mov ebp, dword ptr [0xcef10]
89fdc  mov eax, dword ptr [0xcef14]
89fe1  jmp ecx; jump into the unrolled 8-pixel sequence

// perspective-correct span: every 8 pixels 1/z is inverted, u/z and v/z are divided and the steps are packed
const eax = ((stepU << 16) | (stepV & 0xffff)) >>> 0;                 // 8.8 + 8.8 in one dword
for (let i = 0; i < 8; i++) {
  b = (b + eax) >>> 0;
  screen[q++] = (screen[q] + tex[(b >>> 24) | (((b >>> 8) & 255) << 8)]) & 255;   // dest += texel
}
// glow smear: out = sat(in + round(0.65*previous out)), first along rows then down columns
const v = buf[i] + T[p]; p = Math.min(255, v); buf[i] = p;
